# Maintenance & triage cadence

How Crucible is maintained after v1.0.0. The goal is a project that stays
honest and safe with a small, predictable time budget — not a promise of
enterprise SLAs. Crucible is maintained on a best-effort basis by the project
owner; nothing here is a support contract.

## Issue triage

- **Cadence:** weekly triage pass (aim: within 7 days of a new issue).
- **Labels:** every new issue gets `triage` from the template; triage replaces it
  with an area label (`api`, `sandbox`, `evaluation`, `web`, `infra`, `docs`, …)
  and one of `bug` / `enhancement` / `question`, plus a priority:
  - `P0` — security, data-loss, or containment breach → see below, handled
    immediately, out of band.
  - `P1` — broken core flow (upload → run → evidence → compare → review) on a
    supported path → next release.
  - `P2` — degraded/edge behavior with a workaround → backlog.
  - `P3` — nice-to-have / roadmap → [docs/product/backlog.md](../product/backlog.md).
- **Closing:** stale issues needing reporter input are pinged, then closed after
  30 days of no response; closing is not a verdict and reopening is welcome.

## Pull requests

- Every PR follows [CONTRIBUTING.md](../../CONTRIBUTING.md) and the
  [PR template](../../.github/PULL_REQUEST_TEMPLATE.md) checklist.
- Required to merge: green `pr-validate` (format, lint, mypy-strict,
  import-linter, unit + integration, smoke eval) and `security` checks, plus
  review. Sensitive areas (migrations, evaluator/baseline, security, infra) are
  gated by [CODEOWNERS](../../.github/CODEOWNERS).
- AI-assisted contributions meet the same bar — there is no "generated by a
  model" exemption.

## Dependencies

- **Dependabot** ([.github/dependabot.yml](../../.github/dependabot.yml)) proposes
  updates; they land through normal PR review, never auto-merged for anything
  that can change behavior.
- **Security scanners** run on every PR and on schedule: CodeQL, Semgrep, Trivy,
  Gitleaks, zizmor, pip-audit ([.github/workflows/security.yml](../../.github/workflows/security.yml)).
- **Lockfiles are the source of truth:** `uv.lock` and `pnpm-lock.yaml` are
  committed; updates are reviewed, not chased to latest blindly.
- Target: review dependency/security PRs at least monthly; apply HIGH/CRITICAL
  fixes out of cadence.

## Security response

- Report privately per [SECURITY.md](../../SECURITY.md) — GitHub Security
  Advisories, or the listed email. **Never** a public issue.
- Acknowledgement target: 72 hours. A confirmed containment/data issue is `P0`:
  triaged immediately, fixed on a private branch, released, then disclosed.
- The incident process and severity matrix live in
  [docs/operations/incident-response.md](incident-response.md).

## Releases

- **SemVer** from v1.0.0: MAJOR for breaking API/behavior, MINOR for additive,
  PATCH for fixes. Prompt/model/router/evaluator policies carry their own
  immutable versions; a release records the policy versions it ships (plan §19.3).
- **Checklist per release** (the [v1.0.0 report](../release/v1.0.0.md) is the
  template):
  1. `make check` green; `make eval-run` gate `pass`; security scans clean.
  2. `CHANGELOG.md` updated with measured, dated, honestly-scoped entries.
  3. Version bumped in `pyproject.toml` (and web `package.json` if relevant).
  4. Release report written — measured results only, no invented metrics.
  5. Doc-link check and a public-history secret scan pass.
  6. Tag `vX.Y.Z` from protected `main`; attach the release report.
- Baseline changes for the eval gate require an explicit PR, evidence link, and
  rationale — never a silent re-baseline.

## Cadence summary

| Activity | Cadence |
|---|---|
| Issue triage | Weekly |
| Dependency / security PR review | Monthly (HIGH/CRITICAL: out of cadence) |
| Security report acknowledgement | ≤ 72 h |
| Release | As changes warrant; no fixed calendar |
| Roadmap review | Per release |
